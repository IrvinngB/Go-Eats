### Q3 (CONFIRM): Effect of revoked consent on placing orders

## Defects found that the specs do not cover (add to specs)
1. ORDER CODE COLLISION (high): `OrderRepository.create` uses `seq = len(list_orders()) + 1001` (`repository.py:41`). Seed creates PED-1040..PED-1099 (60 orders), so the first real order gets `PED-1061`, which already exists -> unique violation -> 500. Today the swallowed `.catch(() => {})` hides it; once failures surface (spec "Write failures surface") EVERY checkout would fail on a seeded DB. Same len-based pattern in payments (`TX-{len+9001}`, `payments/repository.py:36`); it does not collide on a fresh seed (TX-9001..9060 -> TX-9061) but is fragile under deletes/concurrency. Add a requirement: unique, collision-free code generation (e.g. max numeric suffix + 1, retry on IntegrityError).
2. Stale `rating` sync: `OrdersView`/store ignore ratings from other roles; out of scope.
3. `PATCH /orders/{code}/courier` has no merchant scope check (any merchant can assign couriers on any order); add to scoping.
4. `api.ts` refresh-failure path clears tokens but has no router/store hook, so "redirect to /login" needs an event/callback; and it must not fire for anonymous public sync (no refresh token -> `tokenStorage.clear()` then reject, which is fine, but must not redirect from the landing).
5. `GET /delivery/couriers` (public) exposes courier phone numbers; noted, out of scope.
